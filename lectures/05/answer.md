## 宿題

- **取り組んだレベル：** 基礎

- **やったこと（変更したファイル・設定・処理、または設計した取得方法）：**  
  `app/config.py`の`RAG_TOP_K`を5から3に変更し、ベクトル検索で取得する資料の件数を減らした。検索件数以外の設定は変更せず、同じ質問に対して変更前後の回答を比較した。

- **比較した質問と、固定した条件（モデル・対象資料など）：**  
  質問：「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」

  回答モデルは両条件とも`gemini-3.5-flash-lite`を使用した。対象資料は講座の検索DBに登録された講義資料とし、質問文、モデル、検索対象および検索方式を固定した。`--trace`オプションを付けて実行し、検索件数のみを変更した。

- **結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：**

  | 評価項目 | 変更前（5件） | 変更後（3件） |
  |---|---|---|
  | 回答の正確性 | 正答 | 正答 |
  | 引用ページ | 第2回 p.52 | 第2回 p.51、p.52 |
  | 回答時間 | 3.66秒 | 2.39秒 |
  | 入力トークン数 | 3,037 | 2,079 |
  | 出力トークン数 | 185 | 195 |
  | モデル応答回数 | 2回 | 2回 |
  | 生成API推定費用 | $0.001374 | $0.001111 |

  どちらの条件でも、LoRAは元の重みを固定して小さな行列による差分のみを学習し、QLoRAはさらに元の重みを4bitに量子化するという内容を正しく回答できた。

  検索件数を減らした結果、回答時間は約34.7%、入力トークン数は約31.5%、推定API費用は約19.1%減少した。

  `--trace`では、両条件で`search_materials`が呼び出され、必要な根拠を含む第2回p.52が検索結果に含まれていることを確認できた。一方、検索クエリは変更前が「LoRA QLoRA 固定 学習 第2回」、変更後が「LoRA 固定 学習 QLoRA 加える」と異なっていた。

- **改善した例と、残る失敗・制約：**  
  今回の質問では、検索件数を3件に減らしても回答の正確性を維持でき、処理時間や入力トークン数、推定費用を削減できた。ただし、必要な根拠が検索順位の低いページに存在する場合、検索件数の削減によって情報を取り逃す可能性がある。

  また、検索クエリも実行ごとに異なっていたため、今回観測された差をすべて検索件数の変更による効果と断定することはできない。各条件1回のみの実行であり、検索された全ページの内訳も確認していないため、一般的な性能の優劣は判断できない。

- **気づき・疑問：**  
  RAGでは検索件数を増やせば必ず回答品質が向上するわけではなく、必要な根拠を確保しつつ、不要な情報を減らすことが重要だと分かった。特に、今回のように必要な情報が上位の検索結果に含まれる場合、少ない検索件数でも十分な回答が得られる可能性がある。

  一方、検索クエリの生成にもLLMが関与するため、検索件数だけの影響を厳密に評価することは難しいと感じた。今後は検索クエリを固定した実験や複数回の測定を行い、回答品質、処理時間、トークン数、費用のバランスから適切な検索件数を検討したい。
